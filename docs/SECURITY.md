# Security and data flows

Status: **Step 8** (2026-10-21). Updated at every step. This document describes what is actually implemented and tested; it is not a compliance statement. We do not claim GDPR compliance, end-to-end encryption, zero data retention or any certification.

## 1. Safeguards in place

### Two-step sign-in (V1.1, 2026-11-13)

- An authenticator app code (TOTP, Supabase Auth). Offered to everyone in the profile; **required for our
  team**: a platform admin without one is sent to set it up before anything else, and our team's powers in
  the database (`private.is_platform_admin()`) exist only in a session that passed it (`aal2`).
- Once a person has a verified second factor, **every request of theirs needs a session that passed it**:
  a pre-request check refuses every API call otherwise (`private.check_request`, `pgrst.db_pre_request`),
  and restrictive policies guard what does not go through the API (real-time messages and participants,
  stored files). A stolen password or sign-in link alone opens nothing.
- The app asks for the code first (`/auth/two-step`, `src/lib/auth/guards.ts`); server actions and routes
  refuse a session that has not passed it.
- Recovery of a lost factor: done by the founder in the Supabase dashboard after checking the person's
  identity (procedure in `docs/COMPLIANCE.md` §15).
- Tests: `tests/integration/mfa.test.ts`, `tests/unit/totp.test.ts`, `e2e/two-step.spec.ts`.
- Compliance readiness dossier (controls, sub-processors, risks, ISO/SOC 2/GDPR mapping, missing steps):
  `docs/COMPLIANCE.md`.

## 2. Data sent to AI providers

Every AI call is built by our server. Providers receive one self-contained request and are not asked to keep anything (no assistants, threads, files or vector stores on their side).

**Important limits today**

- **Hide reduces what providers receive, it does not guarantee it.** Detection is imperfect (uncommon names, client names not entered in the app, unusual formats), a person can turn modes off for a message, amounts are not masked by default, and **images are never masked**.
- **Memory documents and entries are embedded unmasked** (masking would break search by meaning; the question itself is masked since Step 4). Memory content is therefore sent in clear to the embeddings provider (open question 5 in `docs/STATUS.md`: a local embeddings model would avoid it).
- **No EU data residency is configured** with any provider. Data sent to OpenAI, Anthropic or Google may be processed outside the EU.
- **Provider retention** follows each provider's API terms. `store: false` (OpenAI) stops responses being stored for later retrieval; it does not mean zero retention (providers may keep API data for a limited time, e.g. for abuse monitoring, as described in their own terms).
- **Gemini**: the API key must belong to a billing-enabled Google project; on the free tier Google may use the data to improve its products.
- **Dictated speech** goes to OpenAI unmasked (Hide works on text, not on a voice), and so does its transcript when it is tidied up (same provider, before the person reads it). The company switch turns the microphone off for everyone; a person can always type instead.
- **Learning (Cendr Consciousness)** writes AI-extracted facts into a client's memory without a review step for facts the person stated themselves (the founder's choice, CLAUDE.md §11). Safeguards: it runs on our server with the person's own session (only where they may write); the assistant's own claims, and figures or names the person never wrote, go to the person for confirmation instead; personal facts stay out; nothing that still carries a placeholder; a new value supersedes the older one, which stays as history; "Oublier", "Corriger", per-conversation and company switches; each memory can be kept away from chosen AI providers (`blocked_providers`), enforced before any model call. A model can still extract a wrong fact; people correct or forget it. Design and threat model: `docs/CONSCIOUSNESS.md`.
- **Knowledge import** filters private content with word lists and patterns, in French and English: it greatly reduces what reaches the model and the memory, it cannot catch everything (a private matter worded without the listed words, another language). Every proposal is checked again, doubtful ones are set apart unticked, and **nothing is saved without the person ticking it**. The analysis sends the person's own words (filtered and masked) to the company's model provider.
- **Web search** sends queries to the provider's search engine and its results come back from public web pages: a page can contain wrong or misleading text (including instructions aimed at AIs). The answer cites its pages so people can check them; the model's other rules stay in force.
- **Avatar photos** go to OpenAI under its API terms (retention for abuse monitoring may apply; no EU residency configured). The notice shown before upload says so in plain words; it does not claim that OpenAI keeps nothing.

## 3. Data we store

| Data | Where | Notes |
|---|---|---|
| Messages (as typed) and AI answers | Postgres (`messages`) | Readable by participants only (RLS). Not encrypted at application level |
| Attached files and their extracted text | Storage bucket `chat-attachments` (private), `conversation_attachments` | Deleted with the conversation |
| Memory entries | Postgres (`memory_entries`) | Title, content, source, author, dates, and the vector used for search |
| Memory documents | Storage bucket `memory-documents` (private), `documents` (extracted text), `document_chunks` (passages with exact positions and vectors) | Deleted with the document |
| AI suggestions | `memory_suggestions` | Proposed title and content, status, who decided |
| Source Proof | `message_sources` | A **copy** of each cited passage, with its date, kept with the answer. Deleting a document or entry does not delete the copies cited in past answers |
| Hide mappings | `hide_mappings` | Real values behind placeholders, encrypted (AES-256-GCM, key `HIDE_ENCRYPTION_KEY` outside the database), per conversation, deleted with it. No user can read the table |
| What the AI received | `messages.masked_content`, `conversation_attachments.masked_text` | Masked versions, readable by the conversation's participants |
| Sensitive terms | `sensitive_terms` | Visible to the Owner and Hide admins only |

Studio holds Cendr's own tasks, roadmap and documents, for platform admins only: pages answer "not found" to anyone else, every server action checks `platformAdminOrNull()`, and every `scale_*` table, the two search RPCs (security invoker) and the private bucket `scale-files` are behind `private.is_platform_admin()` (tested in `tests/integration/studio.test.ts`). ## 4. Remaining risks before accepting real customer data

- **Release tokens (our console).** `GITHUB_RELEASE_TOKEN` (Vercel) and `RELEASE_TOKEN` (GitHub secret) can change the
  product's code and launch versions. They are limited to this repository and used only by platform-admin server
  actions and the launch workflow; whoever controls a platform admin account can launch a version. Platform admin
  accounts must therefore be protected like production access (their own e-mail, nobody else's).
- **Claude Code changes** are reviewed by a person in the console before they are accepted, and go live only with a
  launch. The workflow lets Claude Code edit files and run the type check, lint and tests only; it cannot change the
  workflows themselves (GitHub refuses it), secrets or existing migrations. A change should still be read before it
  is accepted.
- **The version check** reads the Supabase secret key from the Supabase management API at run time (masked in the logs),
  signs in as two demo accounts with one-time links, and stores captures of the demo company only.

1. Hide is imperfect by nature (see section 2). Real values remain in our database (messages as typed): Hide protects what goes to AI providers, not our own storage.
2. Hosting: a test deployment runs in the EU (Supabase Frankfurt, Vercel `fra1`) on free plans; production plans, backups, monitoring and an incident procedure are still to be set up (`docs/DEPLOY.md`, `docs/ROADMAP.md`).
3. No per-user rate limiting on the API routes beyond monthly credit quotas.
4. Prompt injection: a document or message can try to steer the model. Impact is limited today (the model has no tools and cannot act, and agents only produce drafts), but answers can be misleading — for example an invoice or a contract written to change the extracted figures or hide a clause. Agents' outputs must be reviewed by a person; the notices say so.
5. **Hiring (EU AI Act).** The Application Review Assistant is designed to stay out of automated filtering (no scores, rankings, shortlists or decisions; a person decides; notice shown). Whether a company's use of it falls under the high-risk obligations depends on how it is used; this needs a legal review before the agent is sold for recruitment.
6. File parsing libraries (pdf.js through unpdf, mammoth, exceljs) process untrusted files on our server; no antivirus scan; an isolated parsing worker would reduce the risk.
7. Quotas are checked before each request: simultaneous requests can exceed a limit slightly.
8. Anyone with direct database or service-role credentials (our infrastructure) can technically read content: the platform-admin guarantee is enforced by code and policies, not by cryptography.
9. Claude and Gemini adapters have not yet been exercised against the real APIs.
10. Memory content goes to the embeddings provider in clear (see section 2). Decide between a cloud provider and a local embeddings model before real customer data.
11. Source Proof keeps copies of cited passages after the original is deleted. A request to erase a person's data will also have to remove these copies (no tool for that yet).
12. Prompt injection through memory: a document added to a memory can contain instructions that the AI reads every time the passage is retrieved. Same limited impact as point 4 today, but more persistent.
13. Losing `HIDE_ENCRYPTION_KEY` makes earlier placeholders impossible to restore; leaking it, together with database access, reveals the mapped values (which are also in the messages).
14. Typing a word and seeing it masked tells a member it is on the company's sensitive list (inherent to masking; the list itself is not readable).
15. Sharing history or transferring a conversation shows earlier answers as written: an answer that used a memory the recipient cannot read can carry its content. The app warns only when that answer cited the memory; what people typed themselves is their own decision.
16. The conversation's title (by default the start of its first message) is visible to everyone added to it.
17. A tool's instructions are written by employees and can steer the AI (like any prompt); company-wide tools are reviewed by an Admin before publication, but team tools are not.
18. Confronter sends the same question and context to up to three providers at once: the data flow is three times wider than a normal question.
19. **Render worker**: it holds the Supabase service key (needed to claim jobs and move files). The rendering of AI-written code is kept away from it (separate process and user, no keys in its environment, blocking policy), but the worker's container should also be limited to network access to Supabase only when deployed, and the key should be replaced by a narrowly scoped role later.
20. **Chromium without its own sandbox** in the renderer (HyperFrames' launch options): a browser exploit in AI-written code would reach the render user's process. Mitigated by the separate user, the blocking policy and one job folder per render; an isolated VM per render would be stronger.
21. **GSAP licence** for Motion Design (open question 13 in STATUS.md): a licensing risk, not a security one, to settle before selling the agent.
22. **Content Security Policy** allows inline scripts (`'unsafe-inline'`, no nonce yet): it blocks loading anything from other sites (images, connections, frames), which is what stops data being sent out, but a nonce-based policy would also contain an injected script.
23. **`/api/hide/detect`** (the live highlighting while typing) answers which words of a text are on the company's lists: someone could test many names quickly. Requests are signed-in and limited in size, not rate-limited.
24. **Deploy workflow**: anyone with write access to the repository can run it and change the production database. A protected GitHub "production" environment (required reviewer, main branch only) and actions pinned by commit are to be set up before real customers.
25. Dependencies use version ranges in `package.json` (the lockfile pins them; installs must use it). One moderate advisory in a sub-dependency of the Excel export (`uuid` through `exceljs`, only reachable with an argument we never pass).

## 6. What an external security audit should check

1. **Tenant isolation**, by an attacker holding a valid account in another company: every REST table, RPC, storage path and real-time channel (the database is reachable directly with the public key, not only through the app).
2. **Restricted clients and group conversations**: the permission intersection for the AI (memory, history, Source Proof), history sharing and transfers, including through the AI ("prompt" attacks asking for other clients' data).
3. **Hide**: detection gaps that matter for the customers' data, the placeholder mapping (encryption, key handling), and every path to a provider (chat, files, memory, Confronter, tools, handovers, embeddings).
4. **Authentication**: magic links, invitation flow, session cookies (readable by scripts with Supabase's defaults), account pre-registration, Google sign-in once enabled.
5. **Prompt injection** through documents, e-mails given to agents and tools, and what an injected instruction can make the product display or send.
6. **File handling**: PDF, Word, Excel and video parsing on our servers with hostile files; the render worker and its Chromium (sandbox off) in its deployed container, with network limited to Supabase.
7. **Platform console**: that our team really cannot reach customer content, and the protection of the service key, the Hide key and the deploy credentials.
8. **Configuration of the hosted services**: Supabase Auth settings, storage limits, backups, Vercel environment variables and preview deployments, GitHub repository and workflow permissions.
